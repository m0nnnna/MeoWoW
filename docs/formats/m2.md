# M2

Implementation notes for `crates/m2`. Records what the format actually does and
where it bit us, rather than restating [wowdev.wiki/M2](https://wowdev.wiki/M2).

M2 is the format for every animated object in the game: creatures, characters,
doodads, weapons, spell effects. A stock 3.3.5a install has 22,844 of them.

## Shape

The header is a flat sequence of `(count, offset)` pairs pointing into the rest
of the file. Nothing is self-describing and nothing is bounds-checked, so every
array is validated against the file length at parse time — a bad offset would
otherwise be an out-of-bounds read on data we do not control.

The reader walks header fields **in order** rather than by absolute offset. The
field order *is* the layout, so a missing field shifts everything after it and
fails loudly instead of quietly reading a neighbour.

Version 264 is what 3.3.5a ships, and other versions are rejected: field
positions move between builds, and a wrong layout parses perfectly while
returning nonsense.

## Geometry is not in the `.m2` file

The model holds a vertex pool. The *triangles* live in separate `.skin` files,
one per level of detail — `Foo.m2` is accompanied by `Foo00.skin` (highest
detail) through `Foo03.skin`. `Model::skin_count` says how many exist.

**Indices are two levels deep.** `Skin::triangles` indexes into
`Skin::vertex_map`, and *that* indexes into the model's vertex array. Skipping
the indirection produces geometry that looks plausible and is subtly scrambled,
which is the worst kind of bug to find later.

## Paths in the DBCs are wrong on purpose

`CreatureModelData.model_name` stores `.mdx` paths — a leftover from the
Warcraft III era — while the files shipped since Burning Crusade are `.m2`.
`model_path()` performs the rewrite; a test checks it against all 1,331 rows of
the table rather than a couple of examples.

## Textures are mostly not named by the model

A model's texture slots usually carry `kind != 0`, meaning "the client supplies
this". For creatures, `kind` 11 to 13 are the skins named by
`CreatureDisplayInfo.texture_variation_*`. Only `kind == 0` slots name a file
directly.

So drawing a creature is a three-table walk:

```
CreatureDisplayInfo.id
  -> .model_id            -> CreatureModelData.model_name  (.mdx -> .m2)
  -> .texture_variation_* -> fills the model's runtime texture slots
```

`wow-cli m2 creature <display-id>` runs exactly that.

A batch reaches its texture indirectly as well: `batch.texture_combo_index`
indexes the model's texture combo table, which indexes the texture list. That
double hop is per draw call.

## 16-bit counts overflow, and the fix is a trap

`M2SkinSection.indexCount` and `vertexCount` are `u16`, and a few models exceed
65,535. `World\DUNGEON\Sunwell\Sunwell_Bushes00.skin` has one submesh covering
an index array of 93,456 entries but stores **27,920** — exactly 93,456 minus
65,536. The documented `Level` field carries high bits for the *start* fields,
but it is zero here; the counts simply wrapped.

Submeshes tile the index array in order, so the true span is the distance to the
next submesh's start. **Congruence modulo 65,536 is not sufficient evidence to
use it.** In `Environments\Stars\NexusRaid_SkyA00.skin`, submesh 43 correctly
declares 1,728 indices and sits 67,264 before the next start — and 67,264 is
congruent to 1,728, so a rule that checks only congruence silently corrupts a
valid submesh. That regression was introduced and caught within one survey run.

The repair therefore requires the stored value to be *provably wrong* first —
not a whole number of triangles, or running past the array — and the replacement
to be provably better. `Submesh::counts_repaired` records when it fired.

## Validation

A wrong field offset yields a model that parses cleanly and is nonsense, so
`Model::validate` checks properties the data must have rather than the header:

- **Normals are unit length.** This is the sharpest probe available: they are
  unit vectors by construction, so a wrong vertex stride or intra-vertex offset
  breaks them immediately. Zero normals are tolerated on degenerate vertices.
- **Bone weights sum to 255**, the same idea one field over.
- **Bone parents are in range and acyclic**, since a cycle would hang any
  skeleton walk.

`wow-cli m2 survey` runs all of this across the archive set. Expected result on
a stock install:

```
22779/22844 models parsed, 24626 skins
  9942001 vertices, 15928924 triangles across all levels of detail
  largest model: 35046 vertices, 315 bones
  65 listed paths did not resolve (tombstoned or stale)
no failures
```


## Animation

Each bone carries three tracks — translation, rotation, scale — and every track
holds a **separate keyframe list per sequence**. There is no global timeline:
sampling means picking the sequence first, then the keyframe within it.

A track's timestamps and values are *arrays of arrays*. The outer array has one
entry per sequence and each entry is itself a `(count, offset)` pair. Reading
the outer array as the keyframes directly is the obvious mistake and yields
plausible-looking garbage.

### Rotations are not stored the obvious way

`M2CompQuat` packs four `int16`s spanning `-1..1` with the seam at **zero**
rather than at the numeric midpoint:

| stored | value |
|--------|-------|
| `0` | `-1.0` |
| `32767` | `0.0` |
| `-32768` | `0.0` |
| `-1` | `+1.0` |

So identity is `(32767, 32767, 32767, -1)`, not all `32767`. A plain `v / 32767`
is right only near zero, and the resulting error makes limbs drift rather than
snap — easy to miss by eye.

**Unit length is the test that matters.** Rotation keys are unit quaternions by
construction, so `|q| - 1` is a single number that detects a wrong component
decode, a wrong stride, or reading from the wrong file entirely. Garbage bytes
essentially never decode to a unit quaternion.

### Most animation data is not in the `.m2`

WotLK moved keyframes into external `.anim` files, and this is not optional
detail — `HumanMale.m2` keeps only 5 of 52 sequences inline.

A sequence is inline when **flag `0x20`** is set. Otherwise its keyframes live
in `<model><animId:04>-<variation:02>.anim`, e.g.
`Creature\GnollMelee\GnollMelee0062-00.anim`. Crucially, the *outer* per-sequence
array still lives in the `.m2`; only the inner offsets address the external
file.

Reading a non-inline sequence's tracks out of the `.m2` does not fail — the
offsets land somewhere valid-but-wrong and produce confident nonsense. This is
exactly how the problem surfaced: mean `|q| - 1` was `0.35` for `HumanMale` and
`0.09` for `GnollMelee`, while `BogBeast` — which ships no `.anim` files at all
— was already correct at `0.00002`. That contrast is what identified the cause.
With external files loaded, all three sit at `~0.00002`, which is float
rounding.

**A sequence with no data must produce no keyframes at all.** Simply not loading
the external file is not enough: the offsets still read *something*. Those slots
are cleared explicitly, so the bone falls back to bind pose rather than to
noise.

### Aliases

A bare `0x40` sequence has neither inline data nor an external file; it borrows
another entry's keys via `alias_next`. `0x60` is both alias and inline and
carries its own data, so only the bare case needs following.

### Posing

Rotation and scale happen about the bone's **pivot**, so the local transform is
`T(pivot) · T(translation) · R · S · T(-pivot)`. Omitting the pivot swings every
limb about the model origin instead.

Bones are posed parent-first. M2 stores parents before children by convention,
but that is not guaranteed, so the walk sorts by chain depth — a single
out-of-order bone would otherwise silently lose its parent's transform.

Vertices are already stored in bind pose, so identity matrices reproduce the
unskinned result exactly. No inverse bind matrix is needed; the pivot handling
covers it.

**Zero-scale bones are deliberate.** M2 collapses bones to hide geometry —
`HumanMale` bone 24 has sixteen explicit scale keys sampling to exactly
`(0, 0, 0)`. A singular bone matrix is therefore valid, and asserting
invertibility is wrong.

## Attachments

Where other models hang: a weapon in a hand, a shield on a forearm, a spell
effect at a fingertip. One record is 40 bytes -- `id: u32`, `bone: u16`, two
bytes of padding, `position: [f32; 3]`, and a 20-byte visibility track this
reader skips.

**The position is a model-space point, not an offset from the bone.** On every
character model it is bit-for-bit the pivot of the bone it names, which follows
from how a bone matrix is built (`translate(pivot) * transform *
translate(-pivot)`, so the bind pose is the identity). Drawing an attached
model is therefore `bone_matrix * translate(position)`, and *adding* the
position to the bone's translation instead counts the pivot twice -- which puts
a sword out at arm's length from the fist and never reports anything.

The stride was confirmed by properties rather than by a size. Across all 22,779
models in the archives the ids form a contiguous vocabulary of 50 (0 to 49)
with **zero** out-of-range bone indices; a wrong stride reads ids out of the
middle of floats and produces thousands of distinct values with strays
everywhere. `wow-cli m2 attachments <path>` dumps one model beside the pivots
it names; `--survey` tallies the whole population.

Only two ids are named in code, and both were derived rather than transcribed.
Ids 1 and 2 are a mirrored pair at the ends of the arm chains, each keeping to
its own side of the plane of symmetry (id 1 is on -Y in 684 models against 103
on +Y). An M2's forward is +X, confirmed live by the renderer, and it is drawn
Z-up and right-handed -- so the model's left is +Y, making id 1 the right hand
and id 2 the left. Id 0 sits just outboard of the +Y hand and is the shield,
which corroborates it: a shield is worn in the off hand.

The other 47 ids are real and unnamed. Naming one is a claim about what hangs
there, and this project has a rule about transcribing tables that only produce
placement.

## Particle and ribbon emitters

A torch's flame, a spell's sparks and a sword's trail are not in the `.skin`
file at all. They are *descriptions* -- a bone, a rate, a lifespan, and colour,
alpha and size curves -- and the geometry is made at runtime. 6,429 of the
22,844 models in the archives carry a particle emitter (26,374 emitters between
them) and 317 carry a ribbon (1,572 emitters).

### The strides were measured, not transcribed

A particle record is **476** bytes and a ribbon **176**, and neither number was
taken on trust. `wow-cli m2 emitters --strides` asks the question in the one
way that can come out the other way: read every `(count, offset)` pair out of
every record, and require that all of them point *past* the end of the whole
block and inside the file, with the nearest landing within one 16-byte
alignment pad of the block's end. A stride a word short leaves a later record's
tracks inside the block; a word long runs the block into the data.

| stride | models whose blocks account for their own bytes |
|---|---|
| 464 | 0 / 6,429 |
| 468 | 1,739 / 6,429 |
| 472 | 1,739 / 6,429 |
| **476** | **6,429 / 6,429** |
| 480 | 1,739 / 6,429 |
| 484 | 0 / 6,429 |

**The 1,739 is the whole result.** 6,429 models carry an emitter and 4,690 carry
more than one, so exactly 1,739 have a single record -- and with a single
record only the block's *end* moves, which alignment padding hides a word
either way. Every model with two emitters refutes every neighbouring stride.
Ribbons come out the same shape: 176 fits all 317, the neighbours fit 68, and
317 - 249 multi-ribbon models = 68.

The probe reads the bytes itself rather than asking the `m2` crate, on purpose.
The crate's reading is the thing under test, and a probe that consulted it
would agree with it however wrong both were.

### Two kinds of track, and they are not interchangeable

An emitter carries both:

* **`M2Track`**, the ordinary track used everywhere else in the format. Indexed
  by *animation sequence*, timestamps in milliseconds. Answers "how fast is
  this emitting right now, given what the model is doing".
* **`M2PartTrack`** (the format's `FBlock`), 16 bytes: two `(count, offset)`
  pairs and nothing else -- no interpolation type, no global sequence, no
  per-sequence outer array. Its timestamps are **a fraction of one particle's
  life**, stored as a `u16` over `0..=32767`. Answers "what colour is a
  particle that is two thirds dead".

`Club_1H_Torch_A_01`'s tracks read `0, 16384, 32767`, which is start/half/end
and is what identified the encoding. Reading one kind as the other parses
cleanly and produces nonsense: a lifetime fraction read as a millisecond count
puts every key inside the first thirty-three seconds of the animation, which
for a looping torch is "the last key, forever".

### A particle's colour is 0..255 and a ribbon's is 0..1

The torch's particle colour reads `(255, 72, 0)`, `(223, 138, 47)`,
`(255, 234, 177)` -- orange to pale yellow, which is a flame.
`CelestialDragonWyrm`'s ribbon reads `(0.0, 0.96, 1.0)`. Two records, two
ranges, and getting it backwards gives a plausible-looking dark ramp in one
direction and a blown-out white trail in the other.

Not a guess from two samples: counting the keys with any component above 1.0,
which no normalised colour can have, gives **77,410 of 78,377 particle keys and
0 of 1,572 ribbon keys**. The 967 particle keys under 1.0 are the genuinely
near-black ones.

### Other things the survey settled

* An emitter's `texture` is a **direct index into the model's texture list**,
  not through the texture combo table. The torch names texture 1, which is
  `FLAMELICKSMALL.BLP`; through the combos it would land on the handle's
  runtime slot.
* `emitterType` takes only 1 (plane, 19,193), 2 (sphere, 7,041) and 3 (spline,
  140). No `Unknown` at all -- a byte read at the wrong offset takes dozens of
  values.
* `blendingType` takes 1, 2, 4 and 5, with 4 (additive) 22,347 of 26,374. Value
  3 never appears.
* Flipbook grids are all powers of two: 1x1 (22,826), 8x8 (1,925), 4x4 (1,233).
* `lifespanVary` is a **float**, not the integer some documentation gives it as:
  1,133 emitters set it and none of those decode to the denormals near `1e-43`
  an integer would produce.
* 0 of 26,374 particle emitters and 0 of 1,572 ribbons name a bone or a texture
  that does not exist.

### 653 models are nothing *but* an emitter

A model whose entire content is a flame -- `UndeadFireLarge.m2` is 2,208 bytes
with a 48-byte skin -- has no vertices at all. 653 of the 6,500 emitter-carrying
models are like this, and a loader that reads "no triangles" as "nothing to
draw" makes every one of them invisible. This one did, silently, until the
emitters arrived to be drawn: "the model failed to load" and "the model has
nothing in it" produce the same empty patch of ground.

`wow-cli m2 emitters <path>` dumps one model's emitters with the *values* of
every curve, because an emitter cannot be checked any other way -- a flame is
right when its colour ramp runs orange to pale and its scale ramp grows then
shrinks, and those are visible there and nowhere else until something is drawn.

## Timed events

Everything else in the format is *continuous* -- where a bone is at time `t`,
how fast an emitter is emitting at time `t`. An event is the opposite: a
four-character name, a bone, and a bare list of timestamps per animation
sequence with no value attached at all. It says "at 800ms into the walk cycle,
this happened".

The block sat unparsed for four milestones, and it cost something measurable.
The weapon-impact delay in 4.14 is a constant dialled in by a person watching a
sword, documented as such, *because* "the time from the animation's first frame
to the frame the weapon connects" lives here and nothing read it.

### The stride was measured, and the identifier is what measured it

36 bytes: a `uint32` identifier, a `uint32` argument, a `uint32` bone, a
`C3Vector`, and an `M2TrackBase` -- which is an ordinary track with the *values*
array removed, so its one `(count, offset)` outer array sits at +28 rather than
at +24 where a full track's does.

Two independent checks, and they agree. Byte accounting -- every timestamp array
a record points at must land past the end of the whole block -- fits **4,265 of
4,265** models at 36, where 28 and 32 fit none and 40 and 44 fit 1,343. The
stronger check is that the identifier is a **name**:

| stride | records with four printable identifier bytes |
|---|---|
| 28 | 5,991 of 25,500 (23.5%) |
| 32 | 6,014 of 25,500 (23.6%) |
| **36** | **25,498 of 25,500 (100.0%)** |
| 40 | 5,747 of 25,500 (22.5%) |
| 44 | 5,539 of 25,500 (21.7%) |

A name cannot be arrived at by a coincidence of small integers, which is what
makes this the good half of the measurement: a stride a word out does not
produce plausible-looking events, it produces punctuation.

`wow-cli m2 events <path> --strides` is that table.

### The argument column identified itself, and it confirms the whole record

`$CSD` events carry a `SoundEntries` id in `data`. The human male has six, and
they are 6576, 6919, 6921, 6922 and 6923 -- `ClapSounds`,
`HumanMaleEmoteChicken`, `HumanMaleEmoteCry`, `HumanMaleEmoteKiss` and
`HumanMaleEmoteLaugh`, sounds named for the very model carrying them. Each fires
in exactly the sequence its name matches: `EmoteApplaud` (four times, at 634,
967, 1300 and 1634ms -- an applaud is four claps), `EmoteChicken`, `EmoteCry`,
`EmoteKiss`, `EmoteLaugh`.

No wrong stride and no wrong field offset produces sound names that match the
animation names they fire in. Nothing acts on this: emote sounds are a feature
this client does not have.

### `$FSD` is the footfall, and it had a rival

Two families could be the moment a foot hits the ground.

* **`$FL0`/`$FR0`** for the walk, `$RL0`/`$RR0` for the run, `$BL0`/`$BR0` for
  backing up, `$SL0`/`$SR0` for the shuffles. One per foot, each firing once per
  cycle, positioned at ground level and offset to opposite sides by the same
  distance -- left at +Y, right at -Y.
* **`$FSD`**, at the model's origin, firing more than once.

Both fire twice in a human's walk cycle, so both draw a plausible picture. Three
measurements separate them, and they agree:

1. **The count tracks the number of legs.** The human male's walk has two `$FSD`
   timestamps. The **wolf's has four**, one per paw, and so does its run.
2. **On the wolf they line up.** Each of those four `$FSD` times precedes its
   matching per-foot marker by exactly 33ms -- 34 before 67, 167 before 200, 534
   before 567, 667 before 700. Four times out of four.
3. **On the human male the skeleton says the same thing.** Posing it through the
   walk, the two bones that reach the ground touch down at 255 and 755ms and the
   two that reach it lowest at 330 and 830 -- heel then toe. `$FSD` fires at 266
   and 800, between the pairs both times. `$FR0` fires at 0 and `$FL0` at 533,
   which is the *middle of each foot's stance*. The run says it again: contacts
   at 246 and 580, `$FSD` at 267 and 600, `$RR0`/`$RL0` at 33 and 367.

So the per-foot markers say *where a foot is planted* and `$FSD` says *when it
lands*. `wow-cli m2 events <path> --trace <sequence>` is the third measurement,
and it could have come out the other way.

One trap on the way: the event's own bone has no animation track, so tracing the
event's *own* point through a cycle is a flat line and says nothing. It is the
skeleton that has to be posed. And a posed matrix is a deformation about the
bone's pivot, so where a bone actually ends up is its pivot pushed through its
own matrix -- transforming the origin instead gives how far the model's origin
moved, which for every bone in a walk is a small plausible wobble that is not
the foot.

### The external `.anim` trap, again

A character's walk and run are among the sequences whose keys moved out of the
`.m2`, so an event read without the external files has an empty timestamp list
exactly where the interesting one is. That looks like a model carrying an event
it never fires. `Model::events_with` takes the same map `animated_bones_with`
does, for the same reason.

## Not parsed yet

Lights, cameras, texture transforms, the event identifiers other than `$FSD`
(`$CSD`'s emote sounds, `$HIT` and `$CAH`'s weapon contacts, `$DTH`'s death
thud -- all parsed and none acted on), and the emitter fields that describe
behaviour this renderer does not model (spin and tumble, wind, the follow
terms, `zSource`, spline emitters, geometry and recursion sub-models) are read
and carried but not acted on. Spline interpolation (`Hermite`, `Bezier`) is
sampled linearly for now; the control points sit inline with the values and are
not yet decoded.
